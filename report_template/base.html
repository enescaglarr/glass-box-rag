The mechanism

Where the answer actually comes from

The model never sees the dataset. It sees three rows the retriever chose, pasted into a prompt. Everything the assistant knows about your company arrives through the teal path; the blue path only rewrites it.

Recorded runs

Pick a query, follow it through

Each of these was chosen to stress a different part of the retriever: a clean urgent request, a query full of typos and SMS shorthand, a short low-stakes question, and an angry complaint that maps onto no single intent.

What the traces show

Four runs, four things worth knowing

0.10ms

Search is free; the network is not

FAISS resolves 270 vectors in a tenth of a millisecond. The 0.3–1.0 s a query takes is almost entirely the two API round trips. Scaling the index up costs far less than it looks.

0.71cos

Distance is a usable confidence signal

The three clean queries land at 0.85–0.89 cosine similarity against a single intent. The complaint lands at 0.71 and splits across get_refund and payment_issue — the retriever is telling you it is unsure, in a number you can threshold on.

1 / 99

The index sees 1% of the dataset

270 of 26,872 rows, because the free embedding tier allows 1,000 requests a day. Retrieval quality here is a floor, not a ceiling — the misses are a sampling budget, not a method failure.

2.6–3.5k chars

Context dominates the prompt

The instruction scaffold is ~700 characters. Everything else is three retrieved replies pasted in whole. Prompt cost scales with k, which is why k=3 and not k=10.

100% typo-tolerant

Typos cost nothing

how do i chnge the adress my stuff gets sent 2 retrieved the right intent at the highest similarity of all four runs. Embeddings match meaning, and the dataset itself is 20% deliberate typos.

{{ }}

Placeholders leak into the draft

Retrieved rows carry entity tokens like {{Order Number}}. The model copies them straight into its reply. In production these get filled from a CRM before the agent ever sees the draft.

Operating envelope

The free tier decides the architecture

Model choice here was not about capability. Requests-per-day is the binding constraint, and it varies by two orders of magnitude between models that are otherwise interchangeable for this task.

Every text inside a batched embedding call counts as its own request, so the 1,000/day cap is also a 1,000-rows/day indexing cap. That single number is why build_index.py samples evenly per intent instead of embedding all 26,872 rows — the full set would take about 25 days of quota.
